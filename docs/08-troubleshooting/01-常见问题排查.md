# 常见问题排查

这篇按“现象 -> 先查什么 -> 可以怎么做”的顺序整理。

## 1. 服务启动失败

先确认是运行 Docker、预构建包，还是源码运行。

源码运行建议使用 Python 3.12 及以上，并确认依赖已经安装：

```bash
pip install -r requirements.txt
```

如果是显卡环境，还要按照 CUDA、DirectML 或 Apple Silicon 的版本安装匹配的 Torch、Paddle 和 ONNX Runtime。

## 2. 缺少依赖或模型

如果提示 `ModuleNotFoundError`，先检查 `requirements.txt` 和 README 的环境说明。

如果提示模型文件不存在，检查 `backend/models/` 下对应目录，以及大文件是否已经合并完成。

## 3. 视频处理很慢

常见原因：

- 没有可用 GPU，模型退回 CPU。
- OCR 文本检测耗时较长。
- 使用了 ProPainter。
- 视频分辨率或批大小过高。
- FFmpeg 正在用 CPU 重新编码视频。

可以查看日志中的模型设备信息，并观察 GPU 使用率。

相关配置：

- `inpaintMode`
- `subtitleDetectMode`
- `hardwareAcceleration`
- `sttnMaxLoadNum`
- `propainterMaxLoadNum`

## 4. 去字幕后画面被破坏

先不要急着换模型，优先检查遮罩范围：

1. 处理选区是否太大。
2. `subtitleAreaDeviationPixel` 是否过大。
3. 时间前后扩展是否处理了太多无字幕帧。
4. OCR 是否把水印或其他文字一起检测了。

当前部分修复流程会使用整幅宽度的横向区域，实际修改范围可能比文字框大。

可以先把选区和扩大像素调小，再看结果。

## 5. 字幕残留

可能原因：

- 文字框太小。
- OCR 检测框没有覆盖完整文字。
- 字幕边缘颜色复杂。
- 抽样检测漏掉了短暂字幕。

可以逐步扩大选区或 `subtitleAreaDeviationPixel`。不要一开始把选区扩大到全屏。

## 6. 应该选择哪个修复模式

- 固定位置的普通字幕：先试 `sttn-auto`。
- 需要 OCR 精确定位：试 `sttn-det`。
- 图片、动画或静态背景：试 `lama`。
- 运动剧烈、背景变化明显：试 `propainter`。
- 小面积简单背景：可以试 `opencv`。

ProPainter 最重，但不是所有视频都最好。遮罩准确度通常比单纯更换模型更重要。

## 7. 字幕消失后仍有画面变化

检查：

- `subtitleTimelineBackwardFrameCount`
- `subtitleTimelineForwardFrameCount`
- 指定选区大小
- 检测框是否被错误合并

这些设置过大，会把本来没有字幕的帧也送进修复模型。

## 8. 输出视频没声音

声音由 `merge_audio_to_video()` 使用 FFmpeg 处理。

如果没有声音，先检查：

- 原视频是否真的有音频流。
- 内置 FFmpeg 是否能正常运行。
- 日志中是否出现提取或合并失败。

画面视频会先单独生成，音频是在最后一步复制回去的。

## 9. CLI 不传 `-o` 出错

虽然命令行帮助把输出路径标为可选，但当前代码会在入口处直接使用 `args.output`。

稳妥做法是显式传入输出路径：

```bash
python backend/main.py -i input.mp4 -o output.mp4
```

## 10. 图片处理失败

先确认：

- 文件后缀在支持列表中。
- 图片没有超过 100 MB。
- 图片可以被 OpenCV 正常读取。
- `backend/models/big-lama/` 模型文件完整。

图片模式会锁定 LAMA，并在单张图片上执行一次文本检测。

## 11. Mac 报 `bad CPU type in executable`

这通常是运行了不同架构的二进制程序。可以按照 README 的建议安装 Rosetta，或者使用适合当前架构的 Release 包。

## 12. 取消任务没有立刻结束

服务端会通过任务管理器或进程管理器终止处理子进程。

模型推理、视频编码或 FFmpeg 正在收尾时，停止可能会有短暂延迟。

## 推荐排查顺序

```text
看服务端运行日志
  -> 确认输入和选区
  -> 确认模型模式和设备
  -> 调小遮罩/批大小
  -> 再尝试更换模型
```
